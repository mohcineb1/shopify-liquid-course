# Current external research notes — chapters 31–32

## Chapter 31 — Customers & Accounts

Sources: https://shopify.dev/docs/api/liquid/objects/customer ; https://shopify.dev/docs/api/liquid/objects/order ; https://shopify.dev/docs/api/liquid/objects/transaction ; https://shopify.dev/docs/storefronts/themes/customer-engagement/account-component ; https://shopify.dev/changelog/legacy-customer-accounts-are-deprecated ; https://shopify.dev/changelog/the-shopify-account-component-for-customer-accounts-is-now-a-theme-store-requirement

Verified platform facts: `customer` is globally available when logged in and in customer/account, addresses, order, checkout/customer, gift-card/customer, and order/customer contexts. It is nil elsewhere for anonymous customers. Customer orders and addresses are paginable up to 20 at a time. Current customer properties include addresses, orders, tags, default address, B2B/company fields, payment methods and store credit context. `order` has localized financial/fulfillment/cancellation labels, historic line items, total/total-net-refund distinctions, order attributes/note, shipping, and transactions. `transaction` holds buyer-facing status/gateway details/pending instructions but raw receipts should not be presented indiscriminately.

Legacy customer accounts were deprecated on February 26, 2026. They are unavailable for new stores and existing stores not using them; their final sunset date was to be announced later in 2026. Shopify said theme developers should no longer include legacy customer account Liquid files and recommends `shopify-account` plus customer-account UI extensions for the latest account experience. On July 30, 2026 the `shopify-account` component became a Theme Store requirement for new themes and updates, visible in headers on desktop and mobile. `<shopify-account>` opens a Shopify-controlled account sheet for latest customer accounts; legacy accounts use a direct sign-in link. Themes can style supported aspects but Shopify controls account-sheet behavior.

## Chapter 32 — Content Objects

Sources: https://shopify.dev/docs/api/liquid/objects/article ; https://shopify.dev/docs/api/liquid/objects/search ; https://shopify.dev/docs/api/liquid/objects/predictive_search ; https://shopify.dev/docs/api/liquid/filters/metafield_tag

Verified platform facts: `article` exposes formatted `content`, `excerpt`, `excerpt_or_content`, author, image, tags, comment configuration, comments, comment post URL, dates and metafields. Article comments are published comments, empty if disabled, and paginate up to 50. `search` is server query state with `performed`, terms, results, results count, sort state, result types and filters. Results can be article/page/product; `object_type` must guide rendering. Search filters are empty if results contain more than 1000 products; search result lists paginate up to 50.

`predictive_search` is populated only in a section rendered with the Predictive Search API and Section Rendering API. It exposes performed/terms/types and grouped resources for article, collection, page, product. `metafield_tag` produces type-appropriate HTML; it supports rich_text_field and does not currently support list metafields except list.single_line_text_field and list.metaobject_reference among lists. It is a safer type-aware path than assuming a metafield raw value is generic HTML.

## Chapter 33 — Metafields

Sources: https://shopify.dev/docs/api/liquid/objects/metafield ; https://shopify.dev/docs/storefronts/themes/architecture/settings/dynamic-sources ; https://shopify.dev/docs/api/liquid/filters/metafield_tag ; https://shopify.dev/docs/api/liquid/filters/metafield_text

Verified platform facts: Liquid cannot create metafields; they are created in Shopify admin or through an app. Access uses parent `metafields.namespace.key`; keys `size`, `first`, and `last` should use square-bracket notation to avoid Liquid filter ambiguity. Current object types include text, rich text, product/collection/variant/page/file references, numeric, date/time, URL, JSON, boolean, color, measurement, rating, money; newer docs also discuss metaobject reference types through rendering/dynamic source contracts. Deprecated old types `integer`, `json_string`, and `string` return values directly and lack modern metafield object/filter properties. `metafield.value` returns typed objects, e.g. a product object, JSON object, array, measurement/rating/money object.

List values are iterated with `value`. Reference-list length uses `value.count`; non-reference list length uses `value.size`. `metafield_tag` emits type-aware markup; `metafield_text` emits text representation. Neither currently supports list types except list.single_line_text_field and list.metaobject_reference. For metaobject references/list metaobject references these filters take a `field` parameter restricted to single_line_text_field.

Dynamic sources connect section/block settings—not general theme settings—to compatible resource attributes/metafields/metaobjects in context. Compatibility is based on template resource, resource settings, metaobject storefront visibility/field compatibility, brand attributes, and market custom data. Product-context sections expose product sources; resource settings can create relevant context. Documented limits: 100 dynamic sources in JSON templates, general theme settings, or a section group; 50 in a single setting or static section. Defaults should reference a dynamic source only where its value exists; extra Liquid around a dynamic default is invalid.

## Chapter 34 — Metaobjects

Sources: https://shopify.dev/docs/api/liquid/objects/metaobject ; https://shopify.dev/docs/storefronts/themes/architecture/settings/dynamic-sources ; https://help.shopify.com/en/manual/custom-data/metaobjects/connecting-to-your-online-store/webpages ; https://help.shopify.com/en/manual/custom-data/metaobjects/connecting-to-your-online-store/connecting-metaobjects

Verified platform facts: A metaobject is an entry whose fields are defined by its parent definition. Direct access uses `metaobjects.type.handle` or square brackets. A metaobject’s fields are accessed by their key. In a metaobject template, the `metaobject` Liquid object is the currently rendered entry. If the publishable capability is enabled, only active entries return in Liquid; drafts return nil. Metaobjects with storefront access and compatible fields are dynamic sources; they can be connected directly or via `metaobject_reference` metafields. `metaobject` and `metaobject_list` settings require matching definition types. In an editor, list metaobject fields are added as each entry in a list.

Metaobject entries can become web pages when the definition has Storefront access and Publish entries as web pages / Web pages capability, entries exist, and a metaobject theme template is created. The template can use dynamic sources for entry fields. Web page configuration includes page title/meta description field choice and optional handle customization. Metaobjects can model repeatable records/pages such as ambassadors; current target use cases include locations, size guides, ingredients, brand pages, and FAQs. Storefront access is necessary for display.

## Chapter 35 — The form tag

Sources: https://shopify.dev/docs/api/liquid/tags/form ; https://shopify.dev/docs/api/liquid/objects/form ; https://shopify.dev/docs/api/liquid/objects/form_errors

Verified platform facts: `{% form %}` creates the HTML form element and required hidden inputs for Shopify form endpoint/type. Form types include customer/account flows, contact, product, cart, new_comment, localization, password, etc.; some require an object parameter (e.g. product, cart, new_comment, customer_address). It generates endpoint/action/method/accept charset/hidden `form_type` and `utf8` fields, plus type-specific fields. `currency` form is deprecated in favor of `localization`. `return_to` supports `back`, a relative path, or a routes attribute. HTML attributes are passed as form tag parameters including id/class and data-prefixed attributes.

The `form` object includes form-specific returned values, `errors` (nil if none), `posted_successfully?` (false with errors; customer_address always true), and `id`. Form errors have keys author/body/email/form/password plus `messages` and `translated_fields`, accessed with each error key. `default_errors` can output default messages, while an accessible custom summary can loop errors and attach labels/anchors. Form output must preserve the native tag; avoid hand-building endpoints/hidden auth fields.

## Chapter 36 — Every Form Type

Sources: https://shopify.dev/docs/api/liquid/tags/form ; https://shopify.dev/docs/storefronts/themes/product-merchandising/gift-cards ; https://shopify.dev/themes/customer-engagement/email-consent

Verified platform facts: Native forms are type-specific and some require resource parameters: `product` needs product, `cart` needs cart, `new_comment` needs article, `customer_address` needs customer.new_address or an existing address. `customer` newsletter form must include `type=email` and `name=contact[email]`; customer created through it has accepts_marketing true. `localization` replaces deprecated `currency`. Legacy customer template forms are deprecated in favor of the latest account experience/account component, so account forms must be taught as legacy/maintenance scopes, not presumed new standard surfaces.

Gift-card recipient information is collected as line item properties inside the native product form, including Recipient email, Recipient name, Message, Send on (yyyy-mm-dd), and required `__shopify_send_gift_card_to_recipient` true. Optional timezone offset comes from browser Date getTimezoneOffset; without it the shop timezone is used. It requires normal Add to Cart and is unsupported by accelerated checkout buttons. Limits: recipient name 255 chars, message 200 chars, scheduling up to 90 days. Recipient fields must display form-submission errors. Product/cart properties preserve recipient context.

## Chapter 37 — Section Rendering API

Sources: https://shopify.dev/docs/api/ajax/section-rendering ; https://shopify.dev/docs/storefronts/themes/navigation-search/filtering/storefront-filtering ; https://shopify.dev/docs/api/ajax/reference/cart

Verified platform facts: `?sections=` renders up to five identified sections as a JSON object mapping IDs to HTML. `?section_id=` returns one section as direct HTML. Sections inherit Liquid context of the requested page URL (product/collection/etc.). Section setting values cannot be supplied through this API; existing template/static settings apply or defaults are used. With `sections`, an individual failed/missing published-theme section returns null even with HTTP 200; missing single section_id gives 404. Find IDs through section.id or `shopify-section-[section-id]` wrapper; JSON/group sections receive dynamic IDs. Use locale-aware URLs via window.Shopify.routes.root or current pathname. Full-page-respected query parameters such as q/page also apply to rendered sections.

The API is suitable for progressive partial updates such as filtering/pagination/search/cart display; use bundled section rendering with Cart API for cart mutations when appropriate. Storefront filters are URL state and are AND across filters / OR across values; server response needs query URL preservation. Section rendering cost is server full Liquid render for requested sections plus client HTML parse/DOM replacement; plan no-op guards, smallest necessary section set, cancellation/sequence checks, and effects reinitialization after swapping. Cart endpoints should use locale-aware URLs. Current documented filter maximum is 25; if used, quote as a verified configuration limit.

## Chapter 38 — Cart AJAX API

Sources: https://shopify.dev/docs/api/ajax ; https://shopify.dev/docs/api/ajax/reference/cart

Verified platform facts: Ajax API is only for Shopify-hosted themes, not custom storefronts; GET reads and POST updates current-session cart state; responses are JSON; all requests should use `window.Shopify.routes.root` locale-aware base. It is unauthenticated, has no hard rate limits but standard abuse prevention, cannot read customer/order data or update store data. `/cart.js` reads cart. `/cart/add.js` POST adds one/multiple variants and success returns added line items; different properties/prices/selling plans can split same variant into separate lines. `/cart/change.js` is intended for a particular existing line; `/cart/update.js` updates quantities/note/attributes but variant IDs can be ambiguous for duplicate variant lines and it can add variants if no variant match; line key is recommended but can change when line characteristics change. `/cart/clear.js` clears cart. Quantity error examples use 422 JSON status/message/description for sold out or inventory exceeded; server state remains authority.

Bundled section rendering should be used with cart mutation to return changed cart plus HTML for requested sections in one response; exact sections/sections_url behavior and failure details must be verified in target theme. Optimistic UI requires a precise confirmed server reconciliation and rollback/error announcement. Pub/sub must publish only confirmed/reconciled cart state, include versioning or serialization for overlap, and subscribe components independently; it must not invent transactional authority.

## Chapter 39 — Search & Suggest APIs

Sources: https://shopify.dev/docs/api/ajax/reference/predictive-search ; https://shopify.dev/docs/storefronts/themes/navigation-search/search/predictive-search ; https://shopify.dev/docs/storefronts/themes/navigation-search/search

Verified platform facts: `/search/suggest.json` requires q and returns query/product/collection/page/article resources; default types query/product/collection/page. resources limit range is 1–10/default 10; limit_scope all/default or each; unavailable products show/hide/last (default last). Use locale-aware root. JSON errors: 422 invalid params, 417 unsupported buyer locale, 429 throttle with Retry-After, otherwise 5xx. API returns no more than 10 predictive suggestions per request type. Avoid outputting resource body in multilingual stores because it combines translations. `/search/suggest` with `section_id` returns server-rendered HTML populated with predictive_search object; 404 missing section, 417/422/429 possible. Use Liquid section rather than client template to preserve formatting/locale/merchant content. Main native search form uses routes.search_url, q, and can include options[prefix] last. W3C listbox pattern is Shopify’s illustrated prediction pattern; ARIA combobox needs expanded/controls/active selection and robust keyboard behavior. Debounce input, abort/stale guard, do not query empty values, retain full search form submit fallback.
